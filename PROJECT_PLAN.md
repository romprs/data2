# Проект: Автоматический водяной знак на экране (Screen Watermark / Anti-Leak)

## 1. Цель проекта

Защита от утечки конфиденциальной информации через:
- фотографирование экрана,
- скриншоты,
- печать документов,
- сканирование распечаток.

Механизм: на любой документ/окно, открытое в системе, автоматически накладывается видимый водяной знак с именем авторизованного пользователя (и, при необходимости, датой/временем/ID сессии). Знак должен быть виден на фото, скриншотах, распечатках и сканах, но не мешать обычной работе и редактированию документа.

Это класс задач, который в индустрии закрывают DLP/anti-leak продукты (Microsoft Purview screen watermark, Safetica, ARender, Seclore, Citrix session watermark и т.п.) — далее план учитывает их архитектурные решения.

## 2. Функциональные требования

1. Водяной знак отображается поверх **любого** приложения/окна на экране (а не только внутри одного редактора) — ОС-независимо от того, какой документ открыт (Word, PDF, Excel, браузер, изображение и т.д.).
2. Содержимое знака настраивается типом (`watermark_type`):
   - **простой текст** — произвольный шаблон, поддерживает подстановки имени пользователя, хоста, даты/времени;
   - **учётная запись** — фиксированный, не подменяемый пользователем формат: имя авторизованного пользователя (логин/ФИО), с возможностью добавить дату/время/ID устройства-сессии.
   - **точечный шифрокод** (`dots`, добавлено сверх исходного плана) — вместо читаемого текста тайл из точек, кодирующий логин+время через AES-256-GCM; неотличим на глаз от шума, расшифровывается только офлайн-инструментом с ключом (см. раздел 4.2, `overlay/linux/README.md`).
   - ✅ реализовано для Linux/X11 (`text`/`account`/`dots`, см. статус выше).
3. Знак покрывает весь экран (тайловый паттерн: повторяющийся текст по диагонали или сеткой), а не одна надпись в углу — так его нельзя обрезать кадрированием фото.
   - ✅ реализовано сверх плана: помимо регулярной сетки (`layout: "grid"`, было изначально) добавлен вариант случайного размещения (`layout: "random"` + `density`, RPM 0.7.0) — джиттер-сетка вместо буквально случайных координат, чтобы гарантированно не было наложений (иначе перекрывшиеся `dots`-тайлы не расшифровать). Переключение — тем же общим конфигом, живьём.
4. Знак виден при:
   - фотографировании экрана — так как это часть визуального рендера рабочего стола;
   - создании скриншота — по тем же причинам;
   - печати документа — требует отдельного механизма (см. п. 4.3), т.к. печать не идёт через экранный композитор;
   - сканировании распечатанного документа — обеспечивается автоматически, если знак уже был внедрён в сам отпечаток.
5. Знак **не мешает работе**:
   - полностью прозрачен для мыши и клавиатуры (click-through);
   - низкая непрозрачность / светлый полупрозрачный цвет, не перекрывающий читаемость текста;
   - не встраивается в сохраняемый файл (не портит контент документа при сохранении/экспорте) — если только явно не требуется обратное для конкретных документов.
6. Знак обновляется автоматически при смене пользователя, разрешения экрана, подключении/отключении мониторов.
7. Условие показа настраивается (`mode`):
   - **всегда** — знак виден постоянно, поверх всех окон (поведение по умолчанию);
   - **по списку приложений** — знак виден, только пока открыто хотя бы одно приложение из настраиваемого списка (например, только для офисных пакетов/PDF-читалок/браузера, а не постоянно).
   - ✅ реализовано для Linux/X11: список задаётся подстроками `WM_CLASS` в конфиге, проверка через `_NET_CLIENT_LIST` (см. статус выше). На Windows аналогом будет список исполняемых файлов/заголовков окон через `EnumWindows`/`GetWindowThreadProcessId`.
8. (Опционально, Enterprise) Централизованное управление политикой знака: шаблон текста, включение/выключение по группам пользователей, аудит событий печати/попыток отключения.

## 3. Нефункциональные требования

- Низкое потребление CPU/GPU (оверлей должен перерисовываться редко и дёшево).
- Устойчивость к попыткам отключения обычным пользователем (anti-tamper), но с возможностью legit отключения администратором.
- Поддержка multi-monitor.
- Кроссплатформенность: Windows (приоритет 1, корпоративная среда), macOS (приоритет 2), Linux (приоритет 3).
- Безопасность: knowledge о пользователе (ФИО/логин) берётся из доверенного источника аутентификации (AD/SSO/локальная сессия ОС), не подделывается локально.

## 4. Архитектура решения

Система состоит из трёх независимых, но связанных модулей.

### 4.1 Клиентский агент (фоновая служба)

- Запускается при входе пользователя в систему (автозапуск / служба ОС).
- Получает имя текущего авторизованного пользователя из ОС/корпоративной директории.
- Управляет жизненным циклом оверлея и монитором печати.
- Слушает события: смена пользователя, смена разрешения/состава мониторов, blocking/unlock экрана.
- (Enterprise) Периодически синхронизируется с сервером политик: включён ли знак, какой шаблон текста использовать.

### 4.2 Модуль экранного оверлея (обеспечивает п. 4.1–4.3 функц. требований: скриншот/фото/экран)

Создаёт прозрачное окно поверх всех остальных окон, покрывающее весь виртуальный рабочий стол (все мониторы), с тайловым текстом водяного знака.

Ключевые технические свойства окна:
- **Always-on-top** — поверх всех приложений.
- **Click-through** (прозрачно для ввода) — события мыши/клавиатуры проходят к нижележащим окнам.
- **Полупрозрачное** — не мешает читать содержимое.
- Перерисовывается при смене разрешения/мониторов/пользователя.

Платформенная реализация:
- **Windows**: слой `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOPMOST` (Win32) или окно на базе WinUI/DirectComposition для GPU-композиции без нагрузки на CPU. `WS_EX_TRANSPARENT` даёт click-through.
- **macOS**: `NSWindow` с `level = .screenSaver` (или `.statusBar`), `ignoresMouseEvents = true`, `collectionBehavior` включает показ на всех Spaces. Важно проверить, что окно **не** исключено из захвата экрана (по умолчанию оверлеи можно скрыть от скриншотов через `sharingType`, но нам нужно обратное — знак обязан быть виден на скриншоте).
- **Linux (X11)**: окно с `override_redirect` + `_NET_WM_WINDOW_TYPE_NOTIFICATION`/`_NET_WM_STATE_ABOVE`, click-through через XShape/`_NET_WM_WINDOW_OPACITY` и input region.
- **Linux (Wayland)**: `wlr-layer-shell` протокол (поддерживается не всеми композиторами — существенный риск/ограничение, отметить отдельно).

Это закрывает защиту от **скриншотов** и **фотографирования экрана**, так как знак — часть итогового изображения, которое видит камера или инструмент скриншота (композитор ОС рисует его поверх всего).

Ограничение: некоторые API захвата экрана (напр. macOS ScreenCaptureKit) позволяют программно исключать конкретные окна из захвата — теоретическая лазейка для технически подкованного пользователя. Полностью защититься от этого штатными средствами ОС невозможно; это принимается как остаточный риск (см. раздел 8).

**Статус: реализовано для Linux/X11** (см. [`overlay/linux/`](overlay/linux/)) —
PyQt5-окно с флагами `WindowStaysOnTopHint | Tool | X11BypassWindowManagerHint
| WindowTransparentForInput | WindowDoesNotAcceptFocus`, EWMH-хинты
через `python-xlib` (`_NET_WM_STATE_STICKY` для показа на всех рабочих
столах). Дополнительно к описанному выше плану реализовано:
- условный показ по списку приложений (`mode`/`apps`, п. 7 функц. требований);
- переключаемый тип содержимого, включая `dots` — шифрованный точечный
  код вместо читаемого текста (`watermark_type`, п. 2 функц. требований);
- централизованный конфиг (`/etc/watermark-overlay/config.json` →
  `~/.config/...` → CLI) с живым обновлением без перезапуска процесса;
- системная установка для всех пользователей через RPM +
  `/etc/xdg/autostart` (см. [`packaging/redos/`](packaging/redos/)) —
  закрывает часть требований раздела 4.4/6 (централизованная настройка);
- базовый anti-tamper: обёртка-перезапуск, переживающая `kill`/падение
  процесса (не полноценная защита — см. раздел 6);
- отключение софтверного OpenGL (`QT_XCB_GL_INTEGRATION=none`),
  снижающее RSS процесса примерно вдвое (~115МБ → ~61-66МБ).

Всё перечисленное подтверждено не только headless-тестами под Xvfb, но
и вживую на реальной РЕД ОС 8.0.2 VM (2026-08-18): рендер и
full-screen coverage всех трёх `watermark_type`, click-through,
перезапуск после `kill -9`, декодирование `dots`-скриншота, снятого
этим же реальным X-сеансом.

Windows и macOS — по плану выше, не начаты.

### 4.3 Модуль встраивания знака в печать (обеспечивает печать/скан)

Оверлей на экране **не появляется** на распечатке — печать идёт из приложения напрямую в спулер печати, минуя композитор рабочего стола. Нужен отдельный перехват печати.

Подход:
- **Windows**: кастомный **Print Processor** или **Print Monitor**, регистрируемый в спулере печати (`AddPrintProcessor`/`winspool.drv`), который перехватывает задание на этапе EMF/XPS-спула и дорисовывает водяной знак поверх каждой страницы перед отправкой на физический/виртуальный принтер. Альтернатива с меньшими правами — виртуальный PDF/XPS-принтер-прослойка, куда сначала попадает документ, добавляется знак, затем задание переотправляется на реальный принтер.
- **macOS**: CUPS filter/backend — аналогичная перехватывающая прослойка в очереди печати (`cupsfilter`), модифицирующая PostScript/PDF поток.
- **Linux**: то же самое через CUPS filter.

Поскольку знак становится частью физических пикселей отпечатка, **сканирование** такой бумаги автоматически захватывает знак — отдельного механизма для сканирования не требуется.

### 4.4 (Enterprise, опционально) Сервер политик и аудита

- Хранит настройки: включён/выключен знак, шаблон текста, список групп/пользователей.
- Собирает события: попытки завершить процесс агента, события печати с указанием пользователя — для последующего расследования утечек.
- Не обязателен для MVP (можно захардкодить локальную политику "знак всегда включён").

## 5. Обеспечение "не мешает работе" (п. 5 функц. требований)

- Click-through окно — пользователь физически не может кликнуть по знаку.
- Низкая непрозрачность (например, 8–15% alpha), светло-серый цвет, диагональный повторяющийся паттерн (аналог знака "ЧЕРНОВИК"/"CONFIDENTIAL" в офисных пакетах).
- Знак не входит в буфер обмена, не сохраняется в файл при экспорте/сохранении документа — это чисто визуальный/печатный слой, не модифицирующий исходные данные приложения.
- Возможность точечных исключений (например, презентационный режим/полноэкранное видео) — по политике, не по умолчанию.

## 6. Anti-tamper (защита от отключения)

- Агент работает как системная служба/демон с правами, недоступными обычному пользователю для остановки (Windows Service под SYSTEM, `protected process` где применимо; на macOS — `launchd` daemon; на Linux — `systemd` unit).
- Watchdog-процесс перезапускает оверлей, если его закрыли.
- Логирование попыток остановки службы (для enterprise-аудита).
- Явно фиксируем: 100%-й защиты от technically-advanced пользователя с правами администратора на своей машине быть не может — это ограничение любого клиентского DLP-решения, документируется как остаточный риск.

**Статус для Linux/X11, обновлено 2026-08-18 по факту тестирования на реальной РЕД ОС VM:**

- Проверено эмпирически: `kill <pid>` на процессе, установленном RPM 0.2.0 (только `/etc/xdg/autostart`, без systemd-юнита), **не приводил ни к какому перезапуску** — знак пропадал насовсем до следующего входа в систему. Пример systemd-юнита в `overlay/linux/systemd/` в репозитории существовал, но RPM его никогда не устанавливал — статус в таблице выше "сейчас только `Restart=always`/автозапуск" был неточным, реального перезапуска не было вовсе.
- Исправлено в RPM 0.5.0: `watermark-overlay.wrapper` теперь сам является циклом перезапуска (bash `while true; do python3 ...; [ $? -eq 0 ] && exit 0; sleep 2; done`) — код возврата 0 (осознанная остановка через `mode: "none"` или штатный выход из Qt) уважается как "выключено", любой другой код (сигнал, падение) перезапускает через ~2с. Проверено на реальной VM: `kill -9` на python-процессе → новый процесс поднимается за ~2с; `mode: "none"` → процесс выходит и не перезапускается.
- Это **не** "полноценный" anti-tamper из начала этого раздела: цикл перезапуска выполняется от имени того же непривилегированного пользователя, что и сам оверлей, — его можно убить целиком (весь процесс дерева обёртки), либо просто отключить автозапуск, переопределив `.desktop`-файл в своём `~/.config/autostart`. Требуемый следующий шаг к настоящей защите (root-служба/systemd-unit с правами, недоступными пользователю) остаётся нереализованным.

## 7. Стек технологий (предложение)

| Компонент | Windows | macOS | Linux |
|---|---|---|---|
| Оверлей | C++/C# (WPF/WinUI) + Win32 layered window | Swift + AppKit (`NSWindow`) | ✅ Python + PyQt5 + python-xlib (реализовано; X11 через Qt, без Wayland) |
| Служба/демон | Windows Service (C#/.NET) | launchd daemon | ✅ RPM + `/etc/xdg/autostart` (реализовано); systemd user-unit как альтернатива |
| Перехват печати | Custom Print Processor (C++, Windows Spooler API) | CUPS filter (C) | CUPS filter (C) |
| Получение имени пользователя | Windows API / LDAP-AD | macOS `SecTask`/Directory Services | ✅ `getpass`/`pwd` (реализовано) |
| (Enterprise) сервер политик | REST-сервис, например .NET/Go + Postgres | — | — |

Для MVP на одной платформе план предполагал начать с **Windows**, как
наиболее востребованной в корпоративной среде — по факту разработка
стартовала с Linux (см. "Статус реализации" выше); Windows остаётся
приоритетом для промышленного внедрения.

## 8. Риски и ограничения

1. Продвинутый пользователь с правами администратора может отключить службу или использовать средства захвата экрана в обход композитора (виртуальные камеры, аппаратный HDMI-граббер до этапа композиции невозможен — знак композитора всё равно попадёт в кадр; но программные API, исключающие конкретные окна из захвата, — реальная лазейка на macOS).
2. Wayland на Linux имеет ограниченную и непереносимую поддержку оверлеев (зависит от композитора) — нужен явный disclaimer в roadmap.
3. Перехват печати требует установки драйвера/компонента спулера — повышенные права установки, возможные конфликты с антивирусами/EDR (сигнатурная проверка кастомных print-компонентов).
4. Нагрузка на GPU/CPU от постоянного full-screen оверлея на нескольких мониторах — требует профилирования.
5. Юридический/HR-аспект: сотрудники должны быть уведомлены о мониторинге (политика конфиденциальности/трудовой договор) — не техническая, но обязательная часть внедрения.
6. *(новый, 2026-08-18)* Целостность `dots`-режима: поскольку ключ шифрования обязан быть читаем самим процессом-шифровальщиком, запущенным от имени пользователя (см. раздел 6, вопрос 7 раздела 11), технически подкованный сотрудник теоретически может не только расшифровать чужую метку с той же машины, но и подделать валидный зашифрованный блок от чужого имени — то есть при расследовании утечки нельзя полностью полагаться на `dots`-код как на неопровержимое доказательство без дополнительного привилегированного компонента шифрования.

**Этап 0 — Прототип: ✅ выполнено (Linux/X11 вместо Windows по факту)**

- Проверка производительности и корректности click-through, multi-monitor — пройдена (headless-тесты под Xvfb, см. [`tests/linux/`](tests/linux/)).

**Этап 1 — MVP: ✅ выполнено (Linux/X11)**
- Автозапуск для всех пользователей — реализован через RPM +
  `/etc/xdg/autostart` (сильнее исходного плана: не просто одна служба,
  а системная установка "поставил один раз — работает у всех", см.
  [`packaging/redos/`](packaging/redos/)); устойчивость к смене
  разрешения/мониторов — реализована.
- Anti-tamper: только базовый (перезапуск процесса при `kill`/падении, RPM 0.5.0) — как и планировалось на этом этапе, но фактически заработало только 2026-08-18: до этого пакет ставил лишь автозапуск без перезапуска (см. раздел 6). Полноценный anti-tamper остаётся в разделе 6, не начат.
- Конфигурация знака — реализована шире плана: текст, прозрачность,
  шрифт, угол, отступ, **плюс** условный показ по списку приложений и
  переключаемый тип "текст/учётная запись/точечный шифрокод" (пп. 2, 7
  функц. требований), с централизованным конфигом и живым обновлением
  без перезапуска.
- RPM 0.6.0 (2026-09-03): дефолт пакета сменён с `text` на `dots` — на
  реальной установке у получателя (`corp.amurgpz.ru`) обнаружилось, что
  реализованное переключение само по себе не значит, что знак стал
  менее навязчивым по умолчанию: конфиг из коробки всё равно ставил
  читаемый `text`, пока администратор не поменяет его вручную. Заодно
  `%post` пробует `dnf install` перед `pip` для всех Python-зависимостей
  — на той же установке `pip install numpy/Pillow` не смог достучаться
  до pypi.org (корпоративная сеть без внешнего доступа), тогда как
  `dnf`-репозиторий на той машине был доступен.

## 10. Критерии успеха / тестирование

- Знак виден на скриншоте (Win+PrtScn, Snipping Tool, сторонние утилиты захвата) — 100% случаев.
- Знак виден на фото экрана телефоном при обычном освещении — визуальная проверка.
- Знак присутствует на печатной странице из минимум 3 разных приложений (Word, Adobe Reader, браузер) и минимум 2 разных принтеров/PDF-принтеров.
- Скан распечатанного листа содержит читаемый знак.
- Субъективная оценка "не мешает работе": тестовая группа пользователей работает с документами 1 рабочий день, собирается фидбек.
- CPU/GPU overhead оверлея — не более X% (порог определить на этапе профилирования).
- Попытка обычного пользователя (без прав администратора) закрыть/остановить оверлей — неуспешна.

## 11. Открытые вопросы (требуют решения с заказчиком)

1. ~~Нужна ли поддержка macOS/Linux сразу, или Windows-only на старте?~~ —
   решено по факту: старт с Linux (см. "Статус реализации"). Открыт
   следующий шаг: **Windows или macOS следующим** — какая платформа
   нужнее для перехода к промышленной эксплуатации?
2. Нужен ли централизованный сервер политик (Enterprise) или достаточно локальной конфигурации на каждой машине? Для Linux сейчас есть облегчённый вариант — общий `/etc`-файл конфигурации без сервера (см. Этап 3) — устроит ли он как постоянное решение, или нужен именно сетевой сервер политик/аудита?
3. ~~Формат текста знака: только имя, или имя + дата/время + ID устройства?~~ —
   решено: настраивается (`watermark_type`: `text` с шаблоном `{user}/{host}/{time}`, или `account` — фиксированная учётная запись). Открыт вопрос: нужен ли в `account`-режиме ID устройства/сессии в дополнение к user@host?
4. Требуется ли встраивание знака непосредственно в сохраняемый файл (например, при экспорте в PDF из редактора) как дополнительный уровень защиты, помимо экрана и печати?
5. Юридическое сопровождение: согласие сотрудников на мониторинг.
6. *(новый)* Список приложений для `mode: "app_list"` — фиксированный (задаётся ИТ-отделом централизованно) или пользователь сам может расширять его в своём `~/.config`? Сейчас технически возможно и то, и другое (см. приоритет конфигов в [`overlay/linux/README.md`](overlay/linux/README.md)) — нужно решить, входит ли это в политику безопасности.
7. *(новый, 2026-08-18)* Хранение ключа `dots`-режима: сейчас общий симметричный AES-ключ читает сам процесс оверлея, запущенный от имени обычного пользователя (нужно, чтобы шифровать на лету) — файл смягчён с 0644 до 0640 + выделенная группа, но это не решает главного: пользователь, чью метку шифруют, технически может прочитать тот же ключ и расшифровать чужие метки или подделать свою (подробности — `overlay/linux/README.md`, раздел "Честно про хранение ключа"). Правильное решение — доверенный привилегированный компонент, шифрующий вместо процесса пользователя, либо разовые ключи от сервера политик (раздел 4.4) — нужно решить, стоит ли вкладываться в это на текущем этапе прототипа или отложить до Enterprise-этапа. Дополнительно: локальная группа не распространяется на AD/SSO-подключённые учётные записи — для корпоративного развёртывания это отдельный вопрос интеграции.
